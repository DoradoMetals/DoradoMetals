# The e2e suite against the rebuilt frontend (2026-09-07)

The Playwright harness had not been run since the Next.js factor (N1 + N2,
`docs/waves/nextjs-factor.md`) moved `features/` into `app/<route>/_src_/` and
`shared/`, and since the API passes that made the transport REST. This is what
it found and what was done about it.

## How it was run

Everything against the DEV database, from the `e2e` worktree, exactly as the
harness has always run:

```
pnpm --filter @dorado/contracts build          # api/ imports its dist
pnpm --filter @dorado/api seed:e2e             # the two e2e accounts
pnpm --filter @dorado/api seed:e2e:order       # one disposable purchase order
node api/src/server.ts                         # port 5000, DATABASE_URL = dev
pnpm --filter @dorado/frontend build && start  # port 3000
BASE_URL=http://localhost:3000 pnpm --filter @dorado/frontend e2e
```

`next build` + `next start` rather than `next dev`: the specs' 30s budget is
real, and a cold dev compile of the admin bundle eats it on its own. `pnpm e2e`
is `--grep-invert @maps`, so the billed Google Places spec never ran. No FedEx
label was bought and no Stripe charge was confirmed or captured - the purchase
seed stubs the outside world entirely, and the sales spec creates a TEST-MODE
intent it never confirms.

## Before the suite could run at all: the order seed was broken

`pnpm --filter @dorado/api seed:e2e:order` failed outright, which meant the
admin drawer-work specs had no disposable order to drive. Two separate causes,
both in `api/scripts/seed-e2e-order.mjs` - harness code, not the API.

1. **`TypeError: world.buyLabel is not a function`.** `place()`'s outside-world
   contract (`LIVE` in `src/domains/orders/place.ts`) is
   `{ buyLabel, authorize, confirm }`. The seed's stub still defined
   `buyPostage`, returning the old FedEx-shaped object. The seed exists
   precisely so no label is bought, so the stub is the whole point of it; it
   had simply not moved with the rename. Replaced with `async buyLabel() {}`.

2. **A latent second failure behind the first.** The address step looked for a
   row in the FROZEN `exchange.addresses` by `name`, and when it found none
   called `addressService.create({ userId, address, user_address })` - one
   object, where the service takes three positional arguments
   (`create(userId, address, user_address)`). On a dev database without the
   legacy row this raises rather than seeding. Repointed at
   `places.user_addresses` keyed by `label`, and the call fixed to the real
   signature, returning the book entry's `address`. Both branches verified:
   the existing-row branch by re-running the seed, the create branch by
   calling `create` with a throwaway label and `remove`ing it again.

## The failures, and what each one was

### (a) Frontend broke in the move - `sitemap.ts` calling a client function

`next build` printed, without failing:

```
sitemap products fetch failed: Error: Attempted to call fetchProducts() from
the server but fetchProducts is on the client.
```

`app/sitemap.ts` renders on the server and imports `fetchProducts` from
`@dorado/client`, but that function lives in `packages/client/src/products/
queries.ts`, which is `'use client'` - so every export of it, plain fetcher
included, is a client reference. The sitemap therefore shipped with **no
product URLs at all**, silently, because the call is inside a `try/catch` that
logs and continues.

Fixed in the package rather than the route, because the route is right:
`packages/client/src/products/fetch.ts` (new, no directive) holds `ProductQuery`
and `fetchProducts`; `queries.ts` imports them; `products/index.ts` exports
both. `lint:client-boundary` stays green - the endpoint is still in
`@dorado/client`, which is what that lint is about.

### (a) The design-system `Select` had no accessible name

`admin-purchase-orders.e2e.ts` › *the item controls an admin needs are all
there* looked for four controls as `role=button`. The page snapshot showed the
two add controls as `combobox` with **no name**:

```
- combobox: Add Scrap to Order
- button "Edit" [disabled]
- button "Remove" [disabled]
- combobox: Add New
```

Two things were wrong and only one of them was the spec. Radix's Select trigger
is `role=combobox`, and `packages/components/src/select/Select.tsx` gave it an
accessible name only when the caller passed a `label` - so an unlabelled Select
was an anonymous combobox to a screen reader and to any name-based query.
`aria-label={label == null ? placeholder : undefined}` now names it from the
placeholder it already renders. The spec then asks for the two add controls by
`combobox` role and Edit/Remove by `button`, with the reason recorded inline.
`pnpm --filter @dorado/components test` stays green (326 tests).

### (b) `GET /addresses/get` - the transport is REST now

`admin-sales-order-work.e2e.ts` called `GET /api/addresses/get` and got **500**,
not 404: `addresses/routes.ts` declares `GET /:id`, so `get` was parsed as a
uuid and Postgres raised 22P02. Updated to `GET /api/addresses` (D214's REST
transport item).

### (b) The address wire is a BOOK ENTRY, not a flat row

Same spec, next line. It searched the list for `a.name === 'e2e-order-seed'` and
read `seedAddress.id`. The endpoint answers `AddressBookEntry` objects -
`{ address, user_address, locked, actions }` - and the nickname is
`user_address.label` (`places.user_addresses` has `label`, never `name`; see
CLAUDE.md's note on why `recipient_name` blocks the orders read pivot). Updated
to `a.user_address.label` and `a.address.id`, typed inline.

### (b) `SHIPMENT` is the fulfillment method's CATEGORY, not its type

Same spec: `.find((m) => m.type === 'SHIPMENT')` matched nothing, because
`fulfillments.methods` splits `category` (`SHIPMENT` / `DIRECT`) from `type`
(`CARRIER PICKUP` / `CARRIER DROPOFF` / `DROPSHIP` / ...). The purchase seed
already keys on `category`. Updated to `m.category === 'SHIPMENT'`.

### (b) A race in the sales spec's post-cancel re-open

With the four fixes above the sale was created and worked, and the last
assertion still failed: after `page.reload()` the spec filled the search box and
clicked `tbody tr` immediately, racing the filtered re-render, so the click
landed on a row that was replaced and no drawer opened. The first half of the
same spec already waits for the row to carry the order number before clicking;
the second half now does the same.

### (b) The sales seed hook outgrew the default 30s

`admin-sales-order-work.e2e.ts`'s `beforeAll` builds the whole sale server-side
- a dozen API calls including a real Stripe TEST-MODE intent - and timed out at
the default hook budget under parallel workers. `test.setTimeout(120_000)` in
the hook, matching what the tests in the file already set.

## (c) Real API bugs recorded, not fixed

**None.** Every failure resolved to a spec asserting a shape or URL the API
deliberately changed, to a frontend/design-system defect, or to the seed. No
request produced a response the API was wrong to give.

## Remaining flakiness, deliberately not "fixed"

Three consecutive full runs each ended green with one or two FLAKY tests that
passed on the first retry, and a different spec each time:

| run | flaky | shape |
|---|---|---|
| 6 | admin-impersonation, admin-sales-order-work | banner not visible in 25s; hook timeout |
| 7 | admin-leads | test timeout 30s |
| 8 | customer-checkout-sales | test timeout 120s waiting for the Checkout button |

Every one is TIMEOUT-shaped rather than assertion-shaped, on a different spec
each run, with all workers sharing one dev API and one Postgres. That is
contention, not a defect, and raising individual timeouts to hide it would cost
more than it buys. The sales hook was the one exception worth raising, because
its budget was genuinely wrong for what it does.
