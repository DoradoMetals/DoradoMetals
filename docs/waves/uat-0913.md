## 5. Migrate — two real migration bugs, both fixed

### First abort: `092_the_lifecycle_loses_the_offer_statuses.sql`

```
092_the_lifecycle_loses_the_offer_statuses.sql rolled back:
  column "status" does not exist
```

121 migrations applied before the abort. **Root cause:**
`181_the_order_state_is_derived.sql` (tonight's facts-lane wave, ruling 112)
drops `orders.orders.status` — the order's state is derived now, not stored.
Genesis is regenerated from dev's *current* schema, so a from-nothing build
never creates that column at all. 092 still wrote to it unguarded, three
times. Its sibling files touching the same column —
`030_correct_stale_order_status.sql` and
`180_an_order_is_cancelled_by_a_fact.sql` — were **already** rewritten for
this exact break on 2026-09-12 (both carry `EDITED 2026-09-12 (ruling 112,
facts lane)` comments); 092 was the one file in that family that got missed.

**Fix** (092, following the same pattern as 030/180): wrapped the three
`orders.orders` `UPDATE`s in a guard on `information_schema.columns` for
`orders.orders.status`, so the block is a no-op wherever the column is
already gone. Unlike 030's `cancelled_at`, none of the three retired labels
had a surviving fact column to rewrite onto instead — 'Payment Processing'
and 'Received' are derived from payment/fulfillment/lot facts with no column
to backfill, and 'Rejected' → 'Cancelled' duplicates what 180 already wrote to
`cancelled_at`. Guarded no-op was the correct shape, not a rewrite.

### Second abort (after the first fix, same rebuild): `160_the_lot_is_the_only_join.sql`

```
160_the_lot_is_the_only_join.sql rolled back:
  type "pool_entry" already exists
```

**Root cause:** a copy-paste bug, not a genesis-timing bug on its face, but
exposed the same way. 160's existence guard for the `pool_entry` enum checked
`pg_namespace n.nspname = 'refining'` (copied from the `refining.direction`
guard directly above it), but the `CREATE TYPE` statement it guards creates
`inventory.pool_entry`. On dev's first real run neither name existed, so the
wrong-namespace check still evaluated `NOT EXISTS = true` and the type was
created correctly by accident. On a from-genesis rebuild, `inventory.pool_entry`
already exists (genesis reflects the final, correct namespace), but the guard
is checking `refining.pool_entry` — which doesn't exist — so it reports
"not exists" anyway and `CREATE TYPE` collides with what genesis already made.

**Fix:** corrected the guard to check `n.nspname = 'inventory'`, matching what
the statement actually creates. Verified against genesis
(`000_genesis_schema.sql` has the identical, correctly-namespaced guard for
this same type), and a targeted sweep of every other `pg_type`/`pg_proc`
existence guard across all 194 migrations for the same
guard-checks-schema-X/creates-schema-Y pattern found no other instances.

Both fixes: idempotent, `pnpm --filter @dorado/api lint:migrations` clean
(194 files, no destructive writes to `exchange`), migration number and name
unchanged.
