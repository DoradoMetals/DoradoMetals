# Orders — design against the API on `dev`

Audit of Figma file **Orders** `ymmNlCDLVIfanpRQ7QHMIs` (page `Orders`,
last modified 2026-10-09) against the API in `/home/jtj60/dorado-lanes/main`
on `dev`. Read against `docs/rulings.md`, `docs/design/statuses.md`,
`docs/design/orders-screens.md`, `docs/waves/lot-model.md`,
`docs/waves/pool-spot.md` and rulings 112–126.

Only the Orders page is in scope. Inventory and Pool moved to another file.

Every text fact below was read with **hidden nodes filtered out**, so a row
here is something a viewer actually sees.

**Headline: the API is ahead of these screens, not behind them.** The lot
model, the derived order state, `RP-`/`RS-` numbering, `settlement_type`,
`settled_spot`, the `fulfillments.arrivals` arrival definition, the
adopt-assay read and write, and ruling 112's three refusal classes are all
built. What is missing is mostly (a) the **order list** — no filter, no sort,
no count, no lots on the list item — and (b) a handful of **drawn figures
that no read returns per row** (per-lot settlement price, per-lot profit,
linked-order shipment state). The order screens themselves are close.

Note: `docs/design/orders-screens.md` §1 still says a `received_at` on the
inbound fulfillment is "unchanged and still missing". That is **stale** —
ruling 117 settled it and migrations 184/185 built `fulfillments.arrivals`,
which `order_state.sql` and `position.sql` both read. Nothing is owed there.

## 3. Rulings the design needs that nobody has made

| # | Question | Recommended default |
|---|---|---|
| 1 | Does a customer order have a `Draft` state, or is `Draft` refiner-only? `Order State` draws it; `orders.orders` has no column and `POST /api/orders/admin` places immediately. | **Refiner-only.** Add `WHEN ro.sent_at IS NULL THEN 'Draft'` to `refining_state.sql` and leave `orders.orders` alone — an admin-created customer order is placed, and ruling 85 already says an admin never pays one. |
| 2 | Should `Record settlement` refuse while our total and the refiner's differ, or only warn? (Open since `orders-screens.md` §7.) | **Warn.** It is `confirm` under ruling 112 — business judgment, not a data error. `settlementConfirm` already returns the reason string. |
| 3 | Is a refiner invoice **line** an addressable fact? The Adopt dialog links `ELM-88433`; nothing stores it. | **Yes, one column.** `line_reference` on the refiner lot, written by Record settlement and by the import. A parsed invoice is worth nothing if we cannot cite the line we took a figure from. |
| 4 | Does the SETTLED section of Profit Breakdown list every lot on the order, or only the refiner-assayed ones? | **Only refiner-assayed.** It is what `profit_breakdown.sql` already counts, and ruling 123's profit formula needs a `settled_spot` the bullion lot never has. Bullion margin is a different question (Q6). |
| 5 | A refiner order's `Charges` card draws `Shipping Charge` and omits `Refiner fee`, yet `refining.orders.fee` is what `order_money.total` subtracts. Which charges does a refiner order actually carry? | **Refiner fee, payment charge, pool remediation.** Drop the shipping row from refiner orders — the refiner's own fulfillment cost is not a line we bill — and add the refiner fee, which is the one charge that moves the total today. |
| 6 | Does a customer **sales** order get a margin card at all, and against what cost? | **Not yet.** Drop the card from the sales order. A sale's margin is ask-premium against the stock lot's own cost basis, which is a lot-screen question, not an order-screen one. |
| 7 | Do a text and a call attach to an **order**, or only to a customer? The Messages card sits on the order screen; `crm.sms_messages` and `crm.calls` carry `user_id` and no `order_id`. | **Customer only, for now.** Ruling 116's habit — do not add plumbing before it earns itself. But say so on the card: it is the customer's thread, not this order's, and two orders will show the same messages. If Jacob wants per-order threads, it is a nullable `order_id` on both tables plus a filter, not a new table. |
| 8 | Is the Orders-list `Search orders, customers, lots…` one cross-entity endpoint, or per-tab? | **One endpoint, flat rows.** `GET /api/search?q=` returning `kind · id · reference · label`. Three per-tab searches is three places to keep indexed. |
| 9 | `New lot` in the list header: does a lot exist before an order does? | **No.** Drop the button; the mobile `New order` is the honest one. Every position in `position.sql` is derived from an order or a lineage edge, so an orderless lot has no position and cannot appear in inventory. |
| 10 | `Pending assay` (API, `refining_state.sql`) vs `Pending Assay` (the `Order State` badge `664:12752`). Which casing is law? | **Title Case everywhere**, per `statuses.md` §3's stated convention. One-word change in `refining_state.sql`, and it is a label that drives nothing. |
| 11 | Does a refiner-combined group span two customer purchase orders? The Settlement table draws `Combined · 2481-A + 2481-B` on `PO-2481` and a second row on `PO-2488`. (Open since `orders-screens.md` §7.) | **Allow it.** `inventory.lot_sources` already takes N `batch` edges from any orders, and `view_one.sql`'s `share` is computed per source regardless of which order it came from. Refusing it would mean refusing what the refiner actually did. |
| 12 | Does the order list page need per-chip counts? `orders-screens.md` §3 says "a count per chip"; the drawn chips carry none. | **No counts on chips.** One count line under the bar (already drawn, `715:38931`) is one aggregate read; six chip counts is six, under every filter combination. |
